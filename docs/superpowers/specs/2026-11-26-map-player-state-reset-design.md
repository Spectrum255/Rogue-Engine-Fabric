# 地图箱庭玩家状态完整重置设计

## 目标

补全随机地图场景 `refresh.player_reset=full`：每名玩家首次进入箱庭时建立独立生存状态基线，地图刷新后再次进入时恢复该基线，同时保持现有背包、末影箱、位置和死亡回退策略不变。

## 非目标

- 不重置或接管主背包、装备、副手和末影箱。
- 不改变箱庭出生点、传送位置和朝向。
- 不实现成就、统计、任务进度或全局共享状态重置。
- 不新增客户端界面、命令或网络封包。
- 不实现场景快照、完整存档导入或 ZIP 导入。

## 已确认语义

### 恢复范围

`FULL` 恢复以下玩家状态：

- 生命值。
- 饥饿值、饱和度和耗尽值。
- 氧气供应。
- 经验等级、当前经验进度和总经验。
- 当前状态效果。

不恢复：

- 背包、装备、副手和末影箱。
- 位置、维度、朝向和速度。
- 成就、统计、任务进度。

### 快照归属与基线

每名玩家拥有独立状态文件。玩家首次进入 `FULL` 箱庭时，在库存切换完成后、传送前捕获基线。基线一旦建立，不会因普通离开、死亡或地图刷新而更新。

箱庭刷新只增加 `scene_snapshot.reset_count`。玩家下次进入时，如果其状态文件的已应用水位小于箱庭当前刷新次数，则恢复原始基线，并将水位推进到当前刷新次数。连续多次刷新只触发一次恢复，恢复内容仍是首次进入时的基线。

如果箱庭在玩家首次进入前已经刷新多次，首次进入直接捕获玩家当时状态，并将水位设为当前刷新次数，不追溯恢复不存在的基线。

## 数据模型与存储

状态文件路径：

```text
<world>/data/rogue-engine-fabric/scenes/<instance_uuid>/players/<player_uuid>.dat
```

文件使用版本化 gzip 压缩 NBT，字段包含：

- `schema_version`：当前为 `1`。
- `player_uuid`、`instance_uuid`。
- `health`。
- `food_level`、`saturation_level`、`exhaustion_level`。
- `air_supply`。
- `experience_level`、`experience_progress`、`experience_total`。
- `effects`：状态效果 NBT 列表。
- `applied_reset_count`：非负水位。

`SceneSelectionSnapshot.player_state_path` 在 `FULL` 场景中指向：

```text
scenes/<instance_uuid>/players
```

`NONE` 场景保持为空。旧 `FULL` 快照缺少该字段时，服务按实例 UUID 推导同一受管路径，不修改历史 catalog。

## 进入与重连流程

### 首次进入

1. 现有库存服务完成进入策略，写入稳定 `INSIDE` 会话。
2. 玩家状态服务读取状态文件。
3. 文件不存在时捕获当前生存状态，原子写入基线，水位设为箱庭当前 `reset_count`。
4. 状态文件有效且水位等于当前刷新次数时，不恢复玩家状态。
5. 准备完成后执行传送。

### 刷新后进入

1. 库存服务完成进入策略。
2. 玩家状态服务读取并校验基线。
3. 保存当前生存状态作为内存回滚副本。
4. 应用基线状态。
5. 执行传送。
6. 传送成功后原子写入新的 `applied_reset_count`。
7. 传送被拒绝或取消时恢复内存回滚副本，不推进水位。

水位写入使用替换语义：同一个文件只能保存一份基线，不随刷新次数追加记录。

### 箱庭内重连

玩家加入服务器时，现有库存恢复流程先回滚未完成库存事务。随后玩家状态服务检查当前维度是否对应 `FULL` 地图箱庭，并比较状态水位。需要恢复时直接应用基线，因为玩家已经位于箱庭内，不再触发库存或传送流程。

重连时无法读取、校验或恢复状态文件，则断开连接，不允许玩家带不一致状态继续游戏。

## 刷新与崩溃恢复

地图刷新沿用现有流程：

```text
ACTIVE -> RESETTING -> ACTIVE
```

刷新服务只提交世界重置和 `reset_count`，不读取或修改玩家状态文件。玩家恢复是可根据水位重做的派生操作，因此不新增 WAL 动作。

如果服务器在状态应用后、水位提交前崩溃，玩家下次进入或重连会再次应用同一基线，结果幂等。如果箱庭销毁，玩家状态文件位于场景目录内，随现有场景缓存一起进入隔离区。

## 失败处理

- 首次基线写入失败：取消进入，回滚库存切换，不传送玩家。
- 基线读取、校验或应用失败：取消进入，回滚库存切换，不传送玩家。
- 传送失败：恢复进入前生存状态和库存，不推进水位。
- 传送成功后水位写入失败：保留已恢复的基线状态并记录错误；下次进入重试水位提交，不会改变基线内容。
- 箱庭内重连恢复失败：断开连接。
- `NONE` 场景不读取玩家状态文件，行为保持现状。

## 安全与性能

- 单个状态文件最大 `64 KiB`。
- 状态效果数量最多 `100`。
- 严格校验玩家 UUID、实例 UUID、数值范围和非负水位。
- 使用现有 `AtomicFiles.writeAtomic` 和 `verifyManagedPath`，拒绝路径穿越、符号链接和重解析点。
- 状态读写只发生在进入、重连和传送提交时，不增加常驻 tick 开销。
- 不维护中心索引，不保存全量刷新历史。

## 兼容性

- catalog 和 WAL schema 不变。
- 旧箱庭没有场景快照时继续按普通维度处理。
- 旧 `FULL` 场景首次进入时建立基线。
- `NONE` 场景及现有库存策略行为不变。
- 状态文件随场景缓存归档、隔离和销毁，不额外迁移。

## 验证

### 单元测试

- 状态 NBT 序列化与反序列化往返。
- 空效果与多效果列表。
- 非法 UUID、数值、水位和文件大小拒绝。
- 受管路径校验与损坏文件处理。
- 首次捕获、无需恢复、需要恢复和多次刷新只恢复一次的水位决策。
- `FULL` 与 `NONE` 的 `player_state_path` 快照行为。
- 刷新服务不修改玩家状态基线。

### 服务端冒烟

继续验证地图创建、放置、手动刷新、重置次数持久化、归档和恢复，确认新增玩家状态服务不破坏现有流程。

### 客户端在线验收

1. 进入 `FULL` 箱庭，记录生命、饥饿、氧气、经验和状态效果。
2. 修改上述状态后离开箱庭。
3. 在箱庭无玩家时手动刷新。
4. 再次进入，确认生存状态恢复为首次基线。
5. 确认背包、末影箱和位置仍按原有策略处理。
6. 重复刷新并重连，确认不会重复改变基线或产生额外恢复。

在线验收不需要截图，通过游戏状态和服务器日志确认。
